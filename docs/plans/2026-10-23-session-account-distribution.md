# 会话账号分散修复计划

基线：`079e54bb7db5da44f2ae744ebd51e40244bcb008`，分支 `codex/session-account-routing`。

## 已确认的行为

- 主会话 A 已绑定账号，即使暂时没有请求，也计入该账号已承接的会话数量。
- 新独立主会话 B 优先使用承接会话较少的合格账号，不等待 A 的账号达到请求并发上限。
- 旧主会话及其子代理始终先复用已有有效绑定；负载均衡不迁移这些绑定。
- 用户已确认保留现有故障切换。凭证、额度、模型权限等故障与原有重试策略不在本次修改范围内。
- 保留原 sticky 绑定 TTL、席位宽限时间、租户和账号池权限、配额门禁及队列容量。

## 实施顺序

1. 先增加回归测试并单独提交。覆盖不同优先级账号、首轮已结束、席位宽限已结束、控制面重启，以及后续并行续接。确认基线出现预期失败。
2. 在已有 `sticky_sessions` 表中为根会话绑定增加明确标记，通过应用自动迁移执行。复用原绑定键，不新增账号分配表、不修改已有绑定的账号和 VM。
3. 按仍在绑定 TTL 内的根会话统计账号负载。主会话与所有子代理只计一次；执行结束及短期席位释放不清空统计。已有有效根绑定在续接时补充标记，不重建或批量重新分配。
4. 仅修改 `assignment_mode=session` 且 `strategy=balanced` 的新会话首次分配：先沿用现有资格和可用并发筛选，再比较“根会话数 / 有效并发上限”，然后比较当前请求并发比例，最后以现有优先级、席位占用和额度余量顺序决胜。`device` 和 `fill` 保持现有语义。
5. 在预约成功的同步步骤中记录根绑定及标记，保证并发到达的新会话能看到前一个分配结果。已有绑定优先于上述排序；保留原故障切换代码。
6. 验证持久化、并发预约、子代理、旧绑定、故障切换、数据库迁移和备份恢复相关测试，更新 API 文档，提交修复。报告已验证的提交 SHA。

## 验收条件

- 两个同容量账号、不同优先级、四个陆续建立的独立根会话，在首轮均已结束后分配为 2/2。
- 所有旧会话再次请求、短期席位释放后续接、控制面重启后续接，账号均与首次绑定一致。
- 主会话及多个子代理只贡献一个根会话负载；子代理独立上下文及串行队列保持原行为。
- 新会话分散不跨越租户、API key 账号范围、配额、模型、凭证和手动调度门禁。
- 已有故障切换测试仍通过；负载变化、优先级变化不触发切换。
- 根绑定到期或被原故障流程释放后，不再计入新会话分配负载。

## 验证与发布边界

当前基线的会话路由文件已有 33 个用例通过。用 Node 24 的 `--test-isolation=none --test-reporter=tap` 输出逐用例结果；只输出整个测试文件成功不足以证明每个用例执行。

本次先完成本地代码、测试与提交，不自动 push 或部署。部署前需备份当前数据库和配置；部署后使用运行镜像 digest 或代码哈希确认新代码，并核对现有会话账号映射保持不变。回退代码时不恢复过时数据库，以免删除修复后产生的新绑定。
