# CRAG 面板入站：从最简交付实验到历史复用

本次交付在 vm2api 规范化第三方内嵌图像，并复用已经符合 Messages 结构的历史。**不启用早期最简交付开关，不削减现有 envelope，不修改 CRAG、认证、调度或载荷。** 原生 Claude Code 仍负责构造最终供应商请求；面板不再造一份原生请求。

## 优化过程

| 阶段 | 本地认证回放与取舍 |
| --- | --- |
| 最简探针 | 只交 `model`、`messages` 的普通文本可完成回放，面板业务体从 860 降到 117 B，但 Haiku 最终 `max_tokens` 从 8192 变为 32000，thinking budget 从 8191 变为 31999。首组仅 **3/8** 等价；扩展后 **9/17**（另归一化已证实随机的冷导入 ID 后 **10/17**）。客户端响应全相同也不能判定请求完整。 |
| 逐项补齐 | 保留有效预算、thinking 显示、能力门控的模型、系统提示/历史折叠及缓存默认与 caller 标记。补齐后 **19/19** 客户端终态一致，5 组缓存前缀字节一致；最终行为 **17/19 → 19/19** 的差额只来自是否归一化冷导入 assistant ID。纯文本业务体 641 B，长历史 CPU p95 两次均未改善，因此不切换最简路径。 |
| 第三方入站 | Messages 内的 OpenAI 风格内嵌 `image_url` 在原生 CRAG 槽统一成 `image`，包括 `tool_result` 内嵌块，保留相对顺序及缓存标记。无效内嵌内容或不能保真的 `detail` 返回 400，不送入 worker；HTTP(S) 图片和旧槽沿原路径处理。认证回放 8/8 符合预期：原生/别名两对最终请求等价；三个非法图片及一个非法凭证样本均零 POST、零最终出站。 |
| 从跳步骤改为复用 | 试验中直接跳过第二次 `toStandardAnthropicBody` 有局部收益，但会把对象引用与整流不变量混为一谈。交付版保留每次校验：符合条件的长历史、工具和图片样本，4 次历史重建变为 **1 次重建 + 3 次检查后复用**，另省去 2 次全体深复制。工具重写及回映射只复制有变更的块，顶层清理和最终内容校验照常执行。 |

快路径要求从 `user` 开始且角色严格交替、内容为非空 typed blocks；相邻同角色、system 回合、需修复的提醒和待清理字段保留原整流。官方透传与修复重试不使用 CRAG hop 的共享复制分支。无工具、单 `user` 文本且不超过 4096 个 UTF-16 码元的短请求仍走旧路径。这不是一次遍历或跳过验证，也不是环境去重、隐式 TTL 修复或 CRAG 准入变更。

Magpie 的 Claude TUI `renderClaudeTurn` / `renderParts` 也按结构化内容边界识别工具结果与其后的用户文字。可借鉴保留块与调用配对的原则，不移植其面向 TUI 的文本拼接或提示补充：vm2api 对 CRAG 保留 typed blocks，由原生运行时负责会话导入。

## 面板 CPU

历史 A/B（基线 `1413f435`、优化 `0dbae6cb`）：同一源码以本地 loader 开关复用，真实协议 handler、认证 Unix socket fixture，只有回环网络。WSL2、Node 24.13.0、固定一个 CPU；3 个独立进程，每进程 5 轮，每负载每轮每侧 15 次预热、100 次计量，A/B 交替，共 12,000 次有效计量。`process.cpuUsage()` 包含同进程 fixture、传输及 GC；报文字节数不变。

| 负载 | CPU p50：关 → 开 | CPU p95：关 → 开 |
| --- | ---: | ---: |
| 短文本，未走快路径 | 2.917 → 2.945 ms | 6.698 → 6.942 ms；不宣称提速 |
| 约 270 KiB 历史 | 9.905 → 8.866 ms（−10.5%） | 14.410 → 12.742 ms（−11.6%） |
| 64 个工具 | 3.450 → 3.119 ms（−9.6%） | 6.860 → 5.829 ms（−15.0%） |
| 约 1 MiB 图片 | 7.140 → 5.557 ms（−22.2%） | 11.516 → 9.491 ms（−17.6%） |

上表不是线上延迟、吞吐或内核/模型性能；未测并发饱和及峰值分配，也不能把收益与缩短信封实验相加。

## 100 轮以上原生 Replay

与 CPU 表相同的面板版本；CRAG `79c73d5`（3.1.4），官方 Linux x64 Claude Code 2.1.321。实际 handler → 认证 Unix socket → 原生 CC → 认证 TLS 回环接收端；固定租户及面板逻辑会话，将客户端回复并入下一轮。不执行外部工具，不调用真实供应商。启用 `native_handoff_v1`，逐轮使用新原生进程，不是同一 CC 热进程。

| 样本 | 等价 / 对照 | 复用轮次 | 末轮最终请求（规范化后） |
| --- | ---: | ---: | ---: |
| 文本 + caller 缓存 | 100/100 | 99 | 94,059 B |
| 工具 A：100 批、107 个工具调用（JSON） | 101/101 | 101 | 335,329 B |
| 工具 B：100 批、101 个工具调用（SSE） | 101/101 | 101 | 399,803 B |
| 合计 | **302/302** | 301 | 604 次认证最终出站 |

每轮比较实际 CRAG envelope、解压后的最终出站正文及字节、协议头、缓存前缀、客户端 HTTP/JSON/SSE、用量、完整终态和单次调用计数。只规范化动态请求/原生会话 UUID、计费块动态 `cch` 和形态匹配且经对照确认为随机的冷导入 `diagnostics.previous_message_id`；不调整 JSON 顺序、提示词、工具调用/结果 ID、TTL 或业务内容。两份工具样本都包含最后一批结果及 `end_turn`。抽查 24 条 transcript，取得 23 条且均通过；工具 B 优化侧末轮 transcript 未取得，但该轮的最终出站和客户端终态通过。

首次长跑在宿主内存压力下出现首输出 504 以及模块加载 `ENOMEM`，未计作等价；资源恢复后保留 28 秒首输出期限完整复跑。302 对为上述固定样本的结果，不代表所有输入或实际推理等价。

## 缓存连续性

- 另跑 **100/100** 对：每侧 50 个 JSON、50 个 SSE，模拟上游缓存读写和 `5m` / `1h` 写入分项原样送达客户端。跨轮按 `tools → system → messages` 字节顺序、最多向前看 20 块和虚拟 TTL 建模。仅在当轮尾块打 `5m` 标记时，原生提醒随冷导入移到新用户处，旧消息没有重现相同前缀，**两种计费块处理口径均 0 次复用到消息层**。去掉首个原生计费块时 99 次最深到 system；保留该块仅归一化 `cch` 时 98 次，其余为冷启动。
- **12/12** 对边界回放：固定一个旧消息锚点时可模拟消息层复用；经过 310 秒后只剩 system，超过 `1h` 后全冷。改变业务 system 后只匹配更浅的原生 system 前缀。固定旧锚点是测试变量，不是生产修复。
- 这证明 A/B 缓存请求和用量透传一致，不是 Anthropic 缓存命中或账单证据；没有测供应商最小 token 数、实际 cache key、跨原生会话共享、长工具样本缓存命中。
