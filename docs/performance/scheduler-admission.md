# 调度快照与真实排队计时

## 调度路径

候选筛选通过一次 SQLite 联合查询读取账号与运行状态，并在本轮复用额度、Fable、周额度分配判断所需的账号数据。读取快照时不清理全池、不更新账号统计。

已有席位先检查所在 VM；当该 VM 离开可调度池时，仍按原有席位/粘性规则重新选择。最终 `reserve()` 保持同步，重新读取实时快照并核对凭证、权限、模型、冷却、额度和容量，再更新进程内计数。排队票里的旧快照不能直接作为准入依据。单进程 SQLite 的同步准入方式不变。

归还执行许可时，先处理席位队列，再按原账号队列和非粘性候选队列尝试交接。先通过实时准入并取得许可，再唤醒持有该许可的请求，不广播空位。冷却、额度和配置变化可独立触发重检；定时重检不会重置直连队列的等待预算。需要异步重读候选的请求不保证与已知可用候选之间严格 FIFO。

粘性路由、会话席位和执行许可分别计数：`slotIndex` 不是执行许可。请求取消、构造失败或尝试结束后归还自己持有的许可；已发出的请求由执行路径结束时归还，不因收到取消信号而提前放行其他请求。

健康结果按 VM 和账号合并并发探测，使用完成时间计算 TTL。取消一个调用不会取消其他调用共享的探测。健康写回和过期清理由后台任务完成；心跳只更新运行状态表，并保护较新的心跳、凭证禁用和模型冷却。热重建调度器时停止旧维护定时器。

## 计时口径

- `wait_ms`：已有的总调度耗时。
- `queue_wait_ms`：实际等待容量/席位的队列驻留时间。
- `scheduling_ms`：总调度时间减去实际排队时间。

迁移 `046_request_attempt_scheduler_timing.sql` 为历史行保留 NULL。日志性能条、详情和供应商链分开显示新记录的调度与排队；历史记录显示“调度与排队（未拆分）”，不推算不存在的测量。

## 上游 SQLite 验证

基线：`142d29ad`。条件：两个合成账号/槽位，同一会话已有席位，每轮清空健康缓存；使用 SQLite 语句代理计数，包含 SELECT、INSERT、UPDATE、DELETE。三次结果一致：

| 指标 | 上游基线 | 此修改 |
|---|---:|---:|
| 调度关键路径数据库语句 | 48 | 2 |
| 读取语句 | 40 | 2 |
| 写入语句 | 8 | 0 |
| 健康探测 | 2 | 1 |

新路径的两次读取分别是候选快照和最终准入快照。持久化粘性绑定、特定模型策略以及真实容量排队会产生额外工作，因此这个数字仅描述上述受控场景。SQLite 的本地执行时间不能套用远程 PostgreSQL 的毫秒级性能数据。
