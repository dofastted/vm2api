1. **How one VM boots one cli-node and N slots (default N, cap 20). Handshake frames:**
   - **Boot:** Kin-kernel's `supervisor::spawn` (`supervisor.rs:43-100`) executes the CLI binary (`spec.bin`) with flags `native_cli_args` (`-p`, `--output-format stream-json`, `--verbose`, `--include-partial-messages`, `--no-session-persistence`, `--permission-mode acceptEdits`, `--strict-mcp-config`, `--model <model>`) and injects `CLAUDE_CODE_NATIVE_SLOTS=<N>`. Default N is 20 (`config.rs:10`, `config.rs:39`, `multiplex_cli/mod.rs:136`), capped strictly at 20 (`config.rs:54-58`, `nativeMessagesRunner.ts:49`).
   - **Cli-node startup:** Entrypoint `print.ts:499-506` detects `CLAUDE_CODE_NATIVE_SLOTS` and branches directly into `runNativeMessagesLoop()` (`nativeMessagesRunner.ts:52`). It initializes an in-memory `slots = new Map<string, SlotState>()` for `s00`..`s{N-1}`.
   - **Handshake stdout:** Cli-node writes `host_ready` frame (`nativeMessagesRunner.ts:74-82`) with `{ type: "host_ready", protocol_version: 2, slots: N, system_layout, timezone, capabilities: ["multi_slot", "native_sse", "stateless"], config_hash }`. Cli-node immediately follows by emitting N individual `slot_ready` frames (`nativeMessagesRunner.ts:83-85`): `{ type: "slot_ready", slot_id: "s00" }` through `s19`.

2. **What a "slot" is inside cli-node and what it retains across turns:**
   - **Nature of a slot:** A "slot" in `cli-node` is **NOT** an OS process, **NOT** a worker thread, and **NOT** a persistent in-memory conversation session. It is an in-memory state object in a JavaScript `Map` inside a single process: `{ id: string, phase: 'idle' | 'running' | 'cancelling', jobId?: string, abort?: AbortController, task?: Promise<void> }` (`nativeMessagesRunner.ts:37-43`).
   - **Turn retention inside cli-node:** In `nativeMessagesRunner.ts:201-208`, when the job's async promise settles, `slot.phase = 'idle'` and `slot.jobId`, `slot.abort`, and `slot.task` are set to `undefined`. In `nativeMessagesRunner.ts`, the slot retains **zero conversation history across turns**. Every job turn receives the entire cumulative conversation transcript afresh in `job_start.request.messages`.
   - **Shared heap:** All N slots (up to 20) run concurrently on the **same single Bun process and share the exact same JavaScript heap and garbage collector** (`nativeMessagesRunner.ts:68-72`, `compile-cli-node.ts:74-100`).

3. **Concrete memory retainers for a long session and existing caps:**
   - **Rust Kernel In-Flight Job Retention:** During an active turn, `Runtime.jobs` retains `Job` containing a cloned `MessageRequest` (`mod.rs:1720`, `job.rs:6-17`), which holds all messages and system prompts. Furthermore, `Runtime.sinks` retains `JobSink` with `ByteBudget` of 2 MiB (`JOB_SINK_BYTES = 2 * 1024 * 1024`, `mod.rs:265`) and channel capacity 256 items (`JOB_SINK_ITEMS = 256`, `mod.rs:264`). `Runtime.stream_assemblers` retains tokens for reassembling content blocks (`mod.rs:1247-1251`).
   - **Rust Kernel Waiting Session Retention:** In `src/session.rs:120-147`, when a session is in `Phase::WaitingTool`, `SessionRecord.pending_request` holds the **entire cumulative `MessageRequest`** in memory until resumed or expired.
   - **Cli-node Stream Accumulation:** During an API call, `queryKinMessagesWithStreaming` (`claude.ts:2401-2568`) accumulates every text, thinking, and tool delta in memory in `contentBlocks` arrays.
   - **Stdout Line and Job Caps:** `native_protocol.rs:25-26` sets `MAX_LINE_BYTES = 2 MiB` (lines exceeding 2 MiB dropped) and `MAX_JOB_BYTES = 32 MiB` (`mod.rs:2310-2314`, `charge_job_bytes`: cumulative stdout per job exceeding 32 MiB is dropped).
   - **Session Transcript Cap:** `config.rs:42` and `session.rs:126-130` cap continuation transcripts at `max_session_bytes = 16 * 1024 * 1024` (16 MiB). Requests exceeding 16 MiB fail with `invalid_request`.
   - **Memory Guard & Cgroup Caps:** `memory_guard.rs:19-38` defines baseline limits (`soft: 3 GiB`, `drain: 3.5 GiB`, `reject: 3.75 GiB`, `max_inflight_payload: 256 MiB`, `max_pending: 100`). If a cgroup memory limit is set (`/sys/fs/cgroup/memory.max`, lines 381-386), `effective()` scales all limits proportionally against 4 GiB (`memory_guard.rs:70-103`). For example, in a 512 MiB VM/container (`DEPLOY.md:31`), `soft` is 384 MiB, `drain` is 437.5 MiB, `reject` is 468.75 MiB, and `max_inflight_payload` is 32 MiB.
   - **Why a single slot OOMs:** On long sessions (e.g. 100k+ tokens, 10–20+ MiB JSON), deserializing the massive transcript in cli-node (`parseStdinLine` -> `JSON.parse`) allocates tens of thousands of V8/JSC objects with a 10–20x memory amplification. When `anthropic.beta.messages.create` re-serializes and buffers the payload while concurrent slots stream responses, the process RSS rapidly spikes past the cgroup container limit (512 MiB or 1 GiB), triggering the Linux kernel cgroup OOM killer (`SIGKILL`). `MemoryGuard` does not prevent this because it only checks RSS at turn admission (`mod.rs:1656`, `memory_guard.rs:241-264`) and does not enforce mid-turn memory ceilings.

4. **Kernel slot scheduler: sticky pin, spill, ready queue, admission, hot-path blocking:**
   - **Sticky Pinning:** Session sticky pinning uses `DEFAULT_STICKY_TTL = 24 * 60 * 60` (24 hours, `scheduler.rs:7`). A session key `"{tenant_id}\x1f{session_id}"` maps to a `StickyPin { slot_id, last_used }` (`scheduler.rs:9-12`).
   - **Spill:** In `scheduler.rs:97-108`, if the pinned slot is busy (`slot.phase != SlotPhase::ReadyBlocked`), the scheduler falls back to picking a free slot from `ready`. Crucially, line 131 checks `if !pinned { self.bind_sticky(key, id.clone()); }`, meaning spilled turns do **not** rewrite the session's sticky pin.
   - **Ready Queue & Hot-path O(N) complexity:**
     - In `SlotScheduler::pick` (`scheduler.rs:89-135`), every pick operation runs `self.prune_expired()`, which iterates over the entire `sticky` map: $O(\text{sessions})$.

     - The candidate search scans `self.ready` and performs `slots.iter().any(...)`, which is $O(\text{ready} \times \text{slots})$.

#### conclusions

- One VM hosts exactly one Bun/cli-node process and one Rust kin-kernel process. Slots are logical execution tokens (max 20) inside the single cli-node process, not separate processes or threads.
- Cli-node slots are completely stateless across turns: neither `nativeMessagesRunner.ts` nor `singleProcessSlots.ts` keeps a persistent multi-turn transcript across distinct HTTP requests.
- The root cause of single-slot OOM is that every turn transmits the full, cumulative, uncompacted conversation history through JSON over stdio. A 50–100k token transcript generates massive V8/JSC heap allocations and string copying during `JSON.parse` and SDK parameter processing. In a 512 MiB or 1 GiB container, this easily breaches the cgroup limit and triggers the kernel OOM killer.
- Rust kin-kernel has significant hot-path synchronous overhead: blocking synchronous filesystem reads in `MemoryGuard` (`/proc/<pid>/statm`), repeated full-payload JSON serialization in `serialized_request_bytes`, synchronous logging of every SSE line to disk in `decode_stdout`, and $O(\text{sessions})$ iterations in `SlotScheduler::pick`.
- Go currently only implements egress SOCKS/DNS proxies and TLS socket forwarding. Node performs all HTTP protocol rectification, persona injection, caching rules, and SQLite seat scheduling.
